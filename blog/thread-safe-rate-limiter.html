How I built a thread-safe sliding-window rate limiter

By Edith Njoroge · Software Engineer & AI Domain Expert · 6 min read · rate-limiter-cache repo

Rate limiting is one of those problems that looks trivial until you run it under real traffic. A dict that tracks “how many requests did this caller use in the last minute” is a one-liner. The difficulty is entirely in the details: clock handling, memory hygiene, and correctness when multiple threads hit it at the same moment.

The reference design: sliding window, not fixed window

A fixed window (reset a counter every minute) lets a caller burst — 100 requests at 11:59 and 100 at 12:00 both sail through. A sliding window records timestamps so the window moves with the current time, which is what you actually want. I keep a deque of request timestamps per key and evict anything older than the window. The “allowed now” check is just a length comparison.

def allow(self, key: str) -> bool:
    now = time.monotonic()
    with self._lock:
        q = self._events.setdefault(key, deque())
        while q and now - q[0] > self._window:
            q.popleft()
        if len(q) >= self._limit:
            return False
        q.append(now)
        return True

The part people get wrong: the lock

That with self._lock is not optional. Two threads reading and mutating the same deque — and the same setdefault — without a lock will corrupt state or double-count. The measure of a correct limiter is not the happy path; it is passing a concurrency smoke test. I stress-tested with a pool of threads all calling allow() on a shared key at once, then asserted that the number of grants never exceeded the limit and no keys were lost.

Memory hygiene

If you never evict keys, every caller you’ve ever seen lives in memory forever — a slow leak. I pair the limiter with an LRU cache with O(1) eviction so stale keys are dropped. Knowing when to forget is as important as knowing when to count.

Why this matters: the same discipline — think about concurrency, edge cases, and resource limits up front, then prove the behaviour with tests — is what separates a working demo from a service you’d ship. Open the repo and run pytest: six tests, including a concurrency smoke test, all passing.

The lesson worth keeping: write the test for the failure mode you’re most afraid of, not the one that’s easiest to write.
