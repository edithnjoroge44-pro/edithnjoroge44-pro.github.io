Building a real CLI tool the right way

By Edith Njoroge · Software Engineer & AI Domain Expert · 5 min read · cli-data-tool repo

Most command-line “tools” are a single script with a sys.argv grab-bag and a print statement. That works for one person. A tool you’d ship — or hand to someone else — has a real interface that is easy to use, predictably documented, and safe to test.

Subcommands give it a real interface

Instead of one maze of flags, I expose verbs: summarize (stats on a file), validate (check schema/rules), find (query rows). Each has its own arguments, help text, and behaviour. --help is a proper spec, not an afterthought.

Separate the CLI from the logic

The heaviest mistake is letting parsing and business logic share one file. I keep a cli.py that is only about I/O and argument handling, and a core.py with pure functions that take data and return results. Because the core never touches print or argv, I can unit-test it directly without spawning the process.

Exit codes are part of the contract

Scripts return 0 on success and crash on failure. A real tool returns 0, 1 for a runtime error, and a distinct code for “input is invalid / data failed validation.” That lets an outer script decide what to do based on the result — which is the whole point of automation.

$ tool validate data/example.csv
✓ 1,000 rows · 5 columns · 0 issues
$ echo $?
0

The boring rules that make it robust

  • Handle missing files and empty input gracefully with a clear message, not a traceback.
  • Escape output so it is safe to pipe on any platform.
  • Write tests that call the CLI as a process, using a temp directory fixture, so you test the real contract.
Why this matters: a CLI tool that is typed, documented, exit-code-aware, and test-covered is the kind of small, reusable software engineers reach for every day. It is proof you can build to interface standards — which is exactly what a software engineering role tests.
