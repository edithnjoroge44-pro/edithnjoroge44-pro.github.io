Designing a production REST API: validation, errors, and tests

By Edith Njoroge · Software Engineer & AI Domain Expert · 8 min read · sw-rest-api repo

A tutorial CRUD app returns 200 for everything. A service you would actually ship returns the right thing for every input, including the bad ones. Most of that is unglamorous but decisive: validate early, make errors structured, and prove the behaviour with tests.

Validate at the boundary

The first place bad data can be rejected is the HTTP boundary. I validate required fields, types, and formats before they ever reach the database layer. A malformed payload should never trigger a 500; it should be a 400 with a message that tells the client exactly what to fix.

Structured errors, not string soup

Clients cannot parse “Something went wrong.” I return a consistent JSON error envelope — a machine-readable code, a human message, and per-field detail where relevant — so a front end or another service can react programmatically. Correct status codes matter too: 400 for bad input, 404 for missing, 409 for conflict, 422 for validation.

The layering that keeps it maintainable

route  (parse + validate request)
  ├─ service   (business rules, orchestration)
       └─ repository (only place that touches SQLite)

Separating the route layer from the database layer means you can test business logic in isolation and swap the storage engine without rewriting handlers. It is the difference between an app and a codebase.

Tests are the deliverable, not a nicety

I wrote tests first for the failure cases — blank body returns 400, missing resource returns 404, delete returns 204 — and watched them pass against a real (temporary) SQLite DB. Containers are part of the package too: a Dockerfile plus a CI workflow that runs the suite on every push, so “does it still pass?” is a question the pipeline answers, not a question I have to answer manually.

Why this matters: these are the exact judgment calls a senior engineer makes. Open the repo, run pytest, and every path — happy and unhappy — is covered. That is the point of proof-of-work: show the decisions, not just the result.
